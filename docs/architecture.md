# Architecture du prototype

## Application native

Mangrove est une application Tauri 2. Vue 3 et Tailwind CSS 4 composent son interface dans la WebView système. Vite+ sert à installer les dépendances, développer, vérifier, tester et compiler les assets embarqués. Le moteur Git et SQLite tournent dans le processus Rust natif. Aucun serveur HTTP n’est requis en production.

## Contrat de lecture

`Workspace` est le module central du moteur. Il expose les opérations de lecture du dépôt : ouvrir un dépôt, connaître la progression d’indexation, lire une page de commits, retrouver la position d’un commit, lire ses détails, lire un diff de fichier, consulter le statut des modifications non commitées et lire leur diff. L’adaptateur Tauri appelle ce contrat ; les tests et benchmarks l’exercent indépendamment de la fenêtre native.

Le moteur utilise `git2` / libgit2, avec les transports réseau désactivés. Il n’exécute pas de commande Git ni de hook. Il ne modifie ni le worktree, ni l’index Git, ni les refs, ni la configuration Git. Les permissions Tauri exposent uniquement les douze commandes de lecture et le sélecteur de dossier ; aucun accès shell ou filesystem général n’est accordé à l’interface. Les commandes natives exécutent les lectures sur le pool bloquant, hors du thread d’interface.

Les paramètres et caches propres à l’application peuvent être écrits. Le cache SQLite est placé dans le cache utilisateur de l’OS, hors des dépôts consultés. Le moteur rejette un emplacement de cache contenu dans le worktree, les dossiers Git ou le worktree principal d’un worktree lié, y compris via un lien symbolique. L’ouverture du fichier SQLite et de ses sidecars refuse aussi les symlinks et, sur Unix, les hardlinks. Les tests vérifient ces règles et la conservation des fichiers source. Le contrôle équivalent des hardlinks Windows devra être ajouté et vérifié avant une distribution sur cet OS.

La consultation des stashes n’est pas encore fournie. Les contenus de fichiers, leur historique et le blame passent par quatre commandes natives supplémentaires décrites dans [la consultation des fichiers](file-browser.md). L’historique porte sur les commits accessibles depuis HEAD et les références locales. Les références opérationnelles `refs/t3/checkpoints/`, `refs/stash`, `refs/notes/` et `refs/prefetch/` sont exclues des références affichées, des racines du parcours et de son fingerprint. Leurs seules mises à jour ne relancent pas l’indexation. Un fichier `.git` pointant vers un dossier Git externe conserve le worktree choisi ; les réouvertures utilisent ce worktree. Les ouvertures sont sérialisées avec la lecture du fingerprint pour empêcher un état ancien d’invalider une session plus récente. Un cache supprimé est reconstruit lors d’une réouverture. Un instantané également accessible depuis une branche normale reste visible depuis cette branche.

Les suppressions de fichiers exclus par `skip-worktree` et les entrées indexées `intent-to-add` sont écartées du statut. Un index sparse non pris en charge affiche une erreur explicite sans être développé ni réécrit. Les octets lus via un descripteur sans suivi de liens passent par les filtres libgit2 de nettoyage en mémoire (CRLF et ident), sans écrire de blob ni exécuter de programme externe ; les attributs binaires et texte sont respectés.

Les modifications non commitées sont consultées séparément : les fichiers indexés comparent HEAD à l’index Git (`staged`), les fichiers non indexés comparent l’index au worktree (`unstaged`). Les fichiers non suivis sont présentés avec les fichiers non indexés. Un fichier peut apparaître dans les deux groupes quand des modifications supplémentaires ont suivi sa préparation dans l’index. La lecture d’un diff reçoit le groupe et la clé opaque `fileKey` renvoyée par le statut ; cette clé conserve les octets du chemin Git, indépendamment du nom affiché, y compris pour les noms non UTF-8. Cette lecture ne met pas à jour l’index et n’exécute ni stage, ni unstage, ni commit. Le statut est relu à l’ouverture, au retour du focus dans la fenêtre et sur actualisation manuelle ; il ne dépend pas du cache d’historique. Les limites de contenu et la présentation des fichiers binaires ou des diffs tronqués s’appliquent également à ces lectures. Un dépôt bare expose un statut indisponible (`available: false`), car il n’a pas de worktree.

Les patches non indexés sont construits depuis des buffers lus via des descripteurs de dossier et de fichier, sans suivre les liens des parents ou du fichier final. Un lien symbolique est présenté par sa cible textuelle ; son contenu cible n’est pas ouvert pour produire le patch. Les contrôles de taille portent sur le descripteur effectivement ouvert et la lecture est bornée, même si le fichier grandit. Le scan de statut et la détection des renommages restent assurés par libgit2 ; ces opérations internes peuvent lire ou hacher des fichiers et ne constituent pas une isolation du système de fichiers contre un remplacement concurrent de l’arbre consulté. L’intérieur des sous-modules non indexés n’est pas parcouru.

## Chargement progressif

Une ouverture photographie HEAD et les références, puis lance un parcours topologique. Deux workers d’indexation sont partagés par `Workspace`, avec au plus huit sessions de dépôt. Les commits sont persistés par lots de 256 ; les lecteurs voient des snapshots SQLite cohérents.

Les métadonnées textuelles immuables de commits et leur index FTS5 sont conservés. Un changement de références ou de frontières shallow renouvelle le parcours et son graphe sans reconstruire les métadonnées déjà connues. Les parents effectifs sont relus, car l’approfondissement d’un clone shallow peut les changer sans déplacer les refs. Une génération et l’annulation des anciens travaux empêchent une réponse d’une ancienne ouverture de remplacer la nouvelle. Plusieurs instances du moteur partageant un cache utilisent aussi une garde de génération, vérifiée avant réutilisation d’une session.

La version du fingerprint est renouvelée lorsque les règles de parcours changent. Le masquage des checkpoints reconstruit ainsi les anciens parcours en conservant les métadonnées immuables. Les recherches sont limitées au parcours courant : les anciennes entrées FTS des instantanés ne deviennent pas des résultats visibles.

L’interface demande des pages de 128 lignes et conserve au plus douze pages. La virtualisation limite les éléments DOM aux lignes visibles et à une marge de huit lignes. Le graphe est peint sur Canvas avec un espacement fixe des voies et un déplacement horizontal pour les graphes larges. Dans les résultats de recherche, les liens entre commits non adjacents sont masqués pour éviter un graphe trompeur.

Les onglets ne conservent que leur identité d’interface, leur chemin et leur nom. Une seule instance de `useRepository` et de `useWorkingTree` fournit les données affichées. Chaque changement d’onglet appelle une nouvelle ouverture, annule les lectures précédentes et libère leurs pages, recherche, détails et patch côté interface. Le moteur réutilise son cache SQLite quand le dépôt est inchangé. Fermer le dernier onglet vide la vue et annule les lectures encore en cours. La canonicalisation du chemin renvoyée par le moteur évite les onglets doublons et ne remplace pas l’identité d’interface par l’identifiant de session native.

## Recherche et détails

FTS5 indexe messages, auteurs et emails, avec tokenisation Unicode et préfixes de mots. SHA et noms de références ont une recherche par préfixe. La recherche n’est pas une recherche floue, une recherche de code ni une indexation de tous les blobs historiques. La saisie est temporisée de 160 ms, et les réponses obsolètes sont ignorées.

Les fichiers et patches concernent uniquement le commit sélectionné. Après la préparation du premier diff, les fichiers dont le langage est reconnu sont préparés progressivement en arrière-plan. Au-delà de 1 000 fichiers modifiés, les diffs de commits restent à la demande pour éviter de recalculer un grand diff pour chaque fichier préchargé. Le fichier ouvert prend la priorité ; la lecture des changements locaux suspend ce préchargement. Un merge est comparé à son premier parent. L’affichage est borné : 5 000 fichiers, blobs de 2 Mio, patches de 2 000 lignes ou 512 Kio ; l’interface annonce les données binaires et les résultats tronqués. Ces bornes limitent la taille des réponses ; le calcul Git sous-jacent doit encore être mesuré sur les merges et arbres extrêmes.

La liste des fichiers utilise aussi TanStack Virtual. Seules les lignes visibles et une marge sont montées, avec une hauteur fixe et un focus clavier conservé sur la liste. Le résumé et les en-têtes gardent leur hauteur lorsque le fichier ou le commit sélectionné change.

La sélection dans l’historique exprime immédiatement l’intention de l’utilisateur. Les détails, le fichier, son patch et ses couleurs affichés appartiennent à un même snapshot, remplacé quand la nouvelle préparation est complète. Les générations et annulations empêchent les réponses précédentes de remplacer ce snapshot. Aucun loader animé ne remplace le contenu pendant la lecture ; `aria-busy` indique le travail en cours. Le loader d’ouverture d’un dépôt apparaît seulement après 500 ms et disparaît dès la fin ; une ouverture rapide affiche un fond sombre sans passer par l’accueil.

Par défaut, un clic explicite sur un fichier affiche le diff au centre, avec les détails et la liste des fichiers à droite. Le composant `DiffViewer` est partagé avec la vue compacte. La liste de commits reste montée pendant la lecture du diff, pour conserver ses pages et sa position lorsqu’on revient à l’historique. Les deux vues utilisent le fond sombre du thème.

La coloration syntaxique utilise Shiki dans un Web Worker local chargé à la demande. Les grammaires nécessaires sont chargées progressivement, avec un registre explicite de 39 langages : notamment Vue, Svelte, Astro, TypeScript, PHP, C/C++, Java, Go, Ruby et les formats de configuration. Les fichiers comme Cargo.lock, composer.lock, Makefile et .env sont reconnus par leur nom. Les extraits Vue/Svelte/Astro sans balise de début utilisent les délimiteurs présents, le contexte du hunk et les lignes de code pour amorcer leur bloc script ou style ; un fragment ambigu ne permet pas de retrouver tout le contexte du fichier. Pour les commits comme les changements locaux, le fichier, son patch et sa coloration sont publiés ensemble, y compris lorsque le fichier n’a pas encore été préchargé. Les annotations « No newline at end of file » n’entrent pas dans le code reconstruit et s’affichent sans numéro de ligne. La largeur des numéros dépend du plus grand numéro et de la police du diff. Les tokens sont rendus par interpolation Vue, sans HTML généré ; leur publication est différée pendant une sélection de texte pour préserver la copie. Les versions anciennes et nouvelles de chaque hunk sont analysées séparément pour préserver les commentaires et chaînes multilignes sans mêler les suppressions aux ajouts. Un hunk isolé ne fournit pas le contexte syntaxique absent du patch.

La coloration est limitée à 2 000 lignes, 256 Ki caractères, 20 Ki caractères par ligne et 20 000 tokens en sortie. Les formats inconnus, fichiers binaires, limites dépassées et erreurs conservent le texte brut. Un seul worker analyse un fichier à la fois. Le fond dispose de deux secondes ; un fichier ouvert explicitement dispose de huit secondes pour inclure le premier chargement de sa grammaire. Un fichier préchargé puis ouvert bénéficie de cette même borne, calculée depuis le début de son analyse. Après un dépassement, rouvrir explicitement le fichier réessaie la coloration depuis le patch en cache ; le fond ne réessaie pas en boucle. `createDiffCache` conserve patches et tokens, avec un plafond par cache de 256 fichiers, 8 Mi caractères cumulés et 200 000 tokens. Le fond avance séquentiellement avec une pause de 150 ms entre fichiers et s’arrête au plafond ; le fichier ouvert prend la priorité et peut évincer les anciennes entrées. Un changement de commit, de dépôt ou la fermeture libère le cache concerné et ignore les réponses tardives. Aucun cache de vue n’est conservé par onglet. Les couleurs sont des tokens CSS, afin de changer de thème sans relancer l’analyse.

La sélection « Modifications non commitées » active la préparation progressive des fichiers indexés et non indexés. Leur clé associe la zone (`staged` ou `unstaged`) à la clé opaque du chemin Git ; ni le chemin affiché ni l’index de liste n’identifient ces patches. Le cache local est invalidé au début de chaque actualisation, puis reconstruit avec le nouveau statut, même si les chemins sont inchangés. Le dernier affichage cohérent est conservé pendant ces lectures. Le retour à un commit libère le cache local et arrête sa préparation ; une réponse de statut tardive ne la relance pas. La préparation des commits reste suspendue pendant la consultation des changements locaux. Un appel Git natif déjà lancé peut terminer après son annulation logique ; le cache conserve son emplacement de lecture de fond jusqu’au règlement effectif, pour éviter d’accumuler des lectures.

## Préférences d’interface

Le bouton « + » crée un onglet d’accueil avec les dépôts récents, filtrables par nom ou chemin. Ouvrir un dépôt réutilise cet onglet ; choisir un dépôt déjà ouvert active son onglet existant. Les onglets conservent seulement leur nom et leur chemin. Chaque activation recharge l’unique session et libère les données du dépôt précédent.

Les noms de références contenant `/` forment des dossiers imbriqués dans la sidebar. Les replis sont indépendants pour chaque catégorie de références et sont conservés pendant un rafraîchissement du même dépôt. Un filtre révèle temporairement les dossiers correspondants ; retirer le filtre restaure les replis précédents. Le choix d’une feuille conserve l’identité complète de sa référence Git.

Les trois thèmes utilisent les mêmes tokens CSS, y compris les couleurs du Canvas et des diffs. Le thème Classique, gris avec accents bleus, est le défaut ; Mangrove conserve la palette verte, et Macchiato reprend la palette officielle Catppuccin. Le choix est restauré avant le montage de l’interface. Un changement recolore le graphe sans rouvrir le dépôt.

Les types de changement partagent une même présentation : plus vert pour les ajouts, moins rouge pour les suppressions, crayon jaune pour les modifications et flèche bleue pour les renommages. Les statuts moins courants gardent un symbole distinct. Les listes de fichiers utilisent une ligne compacte avec le dossier atténué et le nom du fichier plus clair ; le chemin complet et le statut restent accessibles au survol. Les fonds de diff utilisent des tokens dédiés par thème pour rendre les blocs ajoutés et supprimés plus visibles. Le code ordinaire et les numéros utilisent la couleur de lecture ; la coloration syntaxique garde les mêmes couleurs sur le contexte, les ajouts et les suppressions. La palette distingue les mots-clés bleus, les types turquoise, les chaînes orange et la ponctuation jaune, avec des fonctions et propriétés claires. Les couleurs syntaxiques atteignent au moins 4,5:1 sur les fonds de lecture et de diff des trois thèmes. La sélection du texte du diff garde un fond à 15 % d’accent et un texte explicite pour rester lisible sur ces blocs.

La taille des textes est une préférence locale restaurée au démarrage. Les raccourcis Cmd/Ctrl avec `+` ou `=` augmentent la taille, avec `-` la réduisent et avec `0` rétablissent le nouveau défaut, soit un pixel au-dessus de la taille initiale du prototype. Le diff possède une taille distincte, initialement à 11 px : `DiffFontControls` l’ajuste sans changer le reste de l’interface. Cette préférence est partagée par les diffs de commits et de fichiers locaux, en vue centrale ou compacte. Les raccourcis globaux ajustent également le diff et le réinitialisent à 11 px avec `0`. L’accueil central conserve seulement le logo Mangrove, l’ouverture d’un dépôt et les accès récents.

Le module `usePaneLayout` conserve les largeurs préférées des panneaux branches et détails dans les préférences de l’application. Le panneau des détails peut occuper tout l’espace restant après les branches et un historique d’au moins 340 px, sans plafond fixe ; réduire la fenêtre ne détruit pas la préférence pour une fenêtre plus grande. Les séparateurs proposent capture du pointeur, annulation, clavier et réinitialisation. Les colonnes d’historique utilisent des container queries, car la largeur d’un panneau peut changer indépendamment de la fenêtre.

## Intégrations à venir

GitHub, GitLab et Bitbucket auront des adaptateurs de lecture distincts, y compris leurs variantes auto-hébergées. Les profils seront des préférences de Mangrove, sans synchronisation vers `.gitconfig`. Les secrets devront rester dans le coffre de l’OS. Le SSH devra réutiliser les clés et agents existants ; l’ajout de clés chez un fournisseur est exclu du périmètre de lecture seule.

L’authentification peut nécessiter une requête POST d’échange de token ; la règle de lecture seule concerne les opérations métier sur les dépôts et fournisseurs, pas seulement les verbes HTTP. Clone et fetch éventuels devront être limités à un cache de dépôt appartenant à Mangrove, jamais au dépôt source sélectionné. Ils ne sont pas implémentés dans ce prototype.

## Choix différés

Le remplacement de libgit2 par `gix`, WebGL et une recherche de contenu historique ne sont pas engagés sans mesures sur des dépôts représentatifs. Le benchmark initial est une référence reproductible, pas une garantie de performances sur tous les monorepos.
