# Architecture de Mangrove

## Application native

Mangrove utilise GPUI pour son interface native. `src-gpui` possède un workspace Cargo indépendant et réutilise `crates/mangrove-core` ; la famille `gpui-pre-*` est verrouillée avec GPUI Kit. Cargo compile et teste l’application et le moteur. Git, SQLite et le rendu de l’interface tournent dans le processus Rust natif ; l’application ne lance ni serveur HTTP ni frontend JavaScript. Les icônes de packaging sont dans `src-gpui/assets/icons`.

## Contrat de lecture

`Workspace` est le module central du moteur. Il expose les opérations de consultation du dépôt et la récupération des références distantes. Les vues GPUI appellent ce contrat ; les tests et benchmarks l’exercent indépendamment de la fenêtre native.

Les opérations de consultation utilisent `git2` / libgit2, avec les transports réseau désactivés. Elles n’exécutent pas de commande Git ni de hook et ne modifient ni le worktree, ni l’index Git, ni les refs, ni la configuration Git. Les vues lancent ces lectures via le `background_executor` de GPUI, hors du thread d’interface. Le sélecteur de dossier natif utilise `rfd` ; une garde centrale évite les ouvertures simultanées et l’annulation conserve l’espace de travail consulté.

`fetch_repository` constitue l’opération d’écriture dédiée : elle reçoit un identifiant de session existante, lance le Git installé sur la machine sans shell et récupère chaque remote sauf ceux configurés avec `skipFetchAll`. Les refspecs explicites mettent à jour `refs/remotes/<remote>/*` et les tags suivis, même lorsqu’un remote possède une configuration de miroir ; les branches locales, le worktree, l’index et la configuration restent inchangés. Les hooks, la récursion des sous-modules, la maintenance automatique et le pruning sont désactivés. Les gestionnaires d’identifiants et l’agent SSH existants sont réutilisés sans invite Git interactive. Les objets LFS ne sont pas téléchargés. Une garde native empêche les fetchs concurrents ; chaque remote dispose d’un délai de deux minutes et les diagnostics sont bornés. Un remote en erreur n’empêche pas les suivants de réussir.

`Mangrove::schedule_fetch` programme le fetch du dépôt actif après l’intervalle mémorisé, puis programme le suivant après sa fin. Un intervalle nul, une ouverture en cours ou un dépôt sans remote ne lance pas de timer. Les changements de dépôt retirent le timer ; les générations empêchent une réponse d’une ancienne session de rafraîchir un autre onglet. Après un fetch, même partiellement réussi, `Mangrove::refresh` relit les références et le moteur réutilise ou renouvelle la session selon le fingerprint. Les vues conservent la recherche et la sélection lors d’une actualisation du même chemin et rechargent les données qui dépendent du statut ou de la nouvelle session. Les demandes d’actualisation superposées sont regroupées ; une demande reçue pendant l’ouverture déclenche une relecture après sa fin. Worktrees, stashes, noms des onglets et récents sont également actualisés. Une navigation remplacée invalide sa restauration.

Les paramètres et caches propres à l’application peuvent être écrits. Le cache SQLite est placé dans le cache utilisateur de l’OS, hors des dépôts consultés. Le moteur rejette un emplacement de cache contenu dans le worktree, les dossiers Git ou le worktree principal d’un worktree lié, y compris via un lien symbolique. L’ouverture du fichier SQLite et de ses sidecars refuse aussi les symlinks et, sur Unix, les hardlinks. Les tests vérifient ces règles et la conservation des fichiers source. Le contrôle équivalent des hardlinks Windows devra être ajouté et vérifié avant une distribution sur cet OS.

La consultation des worktrees et des stashes passe par les méthodes `Workspace::list_worktrees`, `list_stashes`, `stash_details` et `stash_diff`, décrites dans [les contextes de dépôt et le mode Solo](repository-context.md). Leurs sections dédiées restent indépendantes des branches et des tags. Le filtre Solo sélectionne les racines du parcours lors de l’ouverture native, recalcule le graphe et réutilise les métadonnées SQLite existantes. Les contenus de fichiers, leur historique et le blame passent par les méthodes décrites dans [la consultation des fichiers](file-browser.md). L’historique porte sur les commits accessibles depuis HEAD, les branches locales (`refs/heads/`), les branches distantes (`refs/remotes/`) et les tags (`refs/tags/`). Seules ces trois catégories de références sont affichées et prises en compte dans les racines du parcours et son fingerprint. Les mises à jour des autres références ne relancent pas l’indexation. Un fichier `.git` pointant vers un dossier Git externe conserve le worktree choisi ; les réouvertures utilisent ce worktree. Les ouvertures sont sérialisées avec la lecture du fingerprint pour empêcher un état ancien d’invalider une session plus récente. Un cache supprimé est reconstruit lors d’une réouverture. Un instantané également accessible depuis une branche normale reste visible depuis cette branche.

Les suppressions de fichiers exclus par `skip-worktree` et les entrées indexées `intent-to-add` sont écartées du statut. Un index sparse non pris en charge affiche une erreur explicite sans être développé ni réécrit. Les octets lus via un descripteur sans suivi de liens passent par les filtres libgit2 de nettoyage en mémoire (CRLF et ident), sans écrire de blob ni exécuter de programme externe ; les attributs binaires et texte sont respectés.

Les modifications non commitées sont consultées séparément : les fichiers indexés comparent HEAD à l’index Git (`staged`), les fichiers non indexés comparent l’index au worktree (`unstaged`). Les fichiers non suivis sont présentés avec les fichiers non indexés. Un fichier peut apparaître dans les deux groupes quand des modifications supplémentaires ont suivi sa préparation dans l’index. La lecture d’un diff reçoit le groupe et la clé opaque `fileKey` renvoyée par le statut ; cette clé conserve les octets du chemin Git, indépendamment du nom affiché, y compris pour les noms non UTF-8. Cette lecture ne met pas à jour l’index et n’exécute ni stage, ni unstage, ni commit. Le statut est relu à l’ouverture, au retour du focus dans la fenêtre et sur actualisation manuelle ; il ne dépend pas du cache d’historique. Les limites de contenu et la présentation des fichiers binaires ou des diffs tronqués s’appliquent également à ces lectures. Un dépôt bare expose un statut indisponible (`available: false`), car il n’a pas de worktree.

Les patches non indexés sont construits depuis des buffers lus via des descripteurs de dossier et de fichier, sans suivre les liens des parents ou du fichier final. Un lien symbolique est présenté par sa cible textuelle ; son contenu cible n’est pas ouvert pour produire le patch. Les contrôles de taille portent sur le descripteur effectivement ouvert et la lecture est bornée, même si le fichier grandit. Le scan de statut et la détection des renommages restent assurés par libgit2 ; ces opérations internes peuvent lire ou hacher des fichiers et ne constituent pas une isolation du système de fichiers contre un remplacement concurrent de l’arbre consulté. L’intérieur des sous-modules non indexés n’est pas parcouru.

## Orchestration GPUI

`app::Mangrove` possède une seule session affichée et coordonne les vues natives par leurs événements. Les onglets gardent leur identité, nom et chemin ; les données et caches ne sont pas conservés par onglet. `Tabs` fournit une tentative opaque d’ouverture, qui capture la cible à restaurer après un échec et rejette les réponses d’une navigation remplacée. Le chemin canonique renvoyé par le moteur évite les onglets doublons. `RepositoryOpenLane` conserve l’ouverture Git physique jusqu’à sa fin et regroupe les demandes sur le dernier intent ; une ancienne ouverture ne peut donc pas renouveler le moteur après une ouverture plus récente. L’intent porte aussi la navigation à restaurer, qui ne peut pas migrer vers le dépôt suivant. Fermer le dernier onglet vide les vues et invalide les demandes, tout en laissant une lecture native engagée libérer sa lane à sa fin.

`HistoryCache` borne l’historique à douze pages de 128 lignes. Les slots de lecture limitent aussi le travail physique à deux pages et une recherche de position, indépendamment des générations d’interface. Les résultats périmés libèrent ces slots et réveillent les demandes courantes sans publier leurs données. Les listes de worktrees et de stashes appliquent la même règle avec une lecture et un dernier intent par liste. Une absence dans une liste de stashes tronquée ne signifie pas une suppression.

`InspectorView` et `FileBrowser` gardent leurs générations et leur lane Git commune. `FilePresentation` publie l’identité du fichier, son patch, ses tokens, le chargement et l’erreur ensemble. Le dernier choix de fichier pendant une actualisation locale est résolu dans le statut frais par clé opaque et zone. `Selection::None` exprime une absence de sélection sans lancer une lecture de SHA vide. Les caches de patches/coloration restent bornés et les réponses d’un ancien statut ne peuvent pas les remplir.

`virtual_scroll` adapte les `ListState` existants à la géométrie complète des lignes. `RowGeometry` arrondit les frontières cumulées du code aux pixels physiques ; les notices de sidebar partent d’estimations affinées par les seules lignes rendues. Le même handle traduit molette, poignée, zoom et révélation d’une ligne, sans deuxième position de défilement. Le rendu reste limité au viewport et ne lit pas le `ListState` depuis son propre callback de lignes.

`RecentMetadata` protège les noms récents par tickets de lecture et invalidation par chemin. `format` partage les formats des SHA, compteurs, initiales et dates françaises entre les vues. `Preferences` persiste thème, polices, largeurs, intervalle et six dépôts récents dans `mangrove-gpui/preferences.json`, sous le répertoire de configuration utilisateur. Le cache du moteur utilise le répertoire de cache utilisateur sous `dev.mangrove.gpui`.

La fonctionnalité Cargo `app-benchmark` est désactivée par défaut. Elle seule compile le profiler GPUI, les actions de mesure et leurs variables de lancement. Le packaging sépare les bundles courants et de mesure. Le [protocole](performance-gpui-protocol.md) distingue les proxys de présentation des mesures de CPU et de mémoire ; le [rapport](performance-gpui.md) conserve la comparaison historique avec l’ancienne interface retirée.

## Chargement progressif

Une ouverture photographie HEAD et les références, puis lance un parcours topologique. Deux workers d’indexation sont partagés par `Workspace`, avec au plus huit sessions de dépôt. Les commits sont persistés par lots de 256 ; les lecteurs voient des snapshots SQLite cohérents.

Les métadonnées textuelles immuables de commits et leur index FTS5 sont conservés. Un changement de références ou de frontières shallow renouvelle le parcours et son graphe sans reconstruire les métadonnées déjà connues. Les parents effectifs sont relus, car l’approfondissement d’un clone shallow peut les changer sans déplacer les refs. Une génération et l’annulation des anciens travaux empêchent une réponse d’une ancienne ouverture de remplacer la nouvelle. Plusieurs instances du moteur partageant un cache utilisent aussi une garde de génération, vérifiée avant réutilisation d’une session.

La version du fingerprint est renouvelée lorsque les règles de parcours changent. La restriction aux branches, aux tags et à HEAD reconstruit ainsi les anciens parcours en conservant les métadonnées immuables. Les recherches sont limitées au parcours courant : les anciennes entrées FTS des instantanés ne deviennent pas des résultats visibles.

`HistoryView` demande des pages de 128 lignes et conserve au plus douze pages. Un `uniform_list` GPUI construit les lignes demandées par le viewport ; chaque ligne de commit mesure 44 px. Le graphe est peint par `graph` avec le Canvas GPUI, un espacement fixe des voies et un déplacement horizontal pour les graphes larges. Dans les résultats de recherche, les liens entre commits non adjacents sont masqués pour éviter un graphe trompeur. Le moteur réutilise son cache SQLite quand le dépôt est inchangé.

## Recherche et détails

FTS5 indexe messages, auteurs et emails, avec tokenisation Unicode et préfixes de mots. SHA et noms de références ont une recherche par préfixe. La recherche n’est pas une recherche floue, une recherche de code ni une indexation de tous les blobs historiques. La saisie est temporisée de 160 ms, et les réponses obsolètes sont ignorées.

Les fichiers et patches concernent uniquement le commit sélectionné. Après la préparation du premier diff, les fichiers dont le langage est reconnu sont préparés progressivement en arrière-plan. Au-delà de 1 000 fichiers modifiés, les diffs de commits restent à la demande pour éviter de recalculer un grand diff pour chaque fichier préchargé. Le fichier ouvert prend la priorité ; la lecture des changements locaux suspend ce préchargement. Un merge est comparé à son premier parent. L’affichage est borné : 5 000 fichiers, blobs de 2 Mio, patches de 2 000 lignes ou 512 Kio ; l’interface annonce les données binaires et les résultats tronqués. Ces bornes limitent la taille des réponses ; le calcul Git sous-jacent doit encore être mesuré sur les merges et arbres extrêmes.

La liste des fichiers utilise un `uniform_list` GPUI, avec une hauteur fixe et un focus clavier conservé sur la liste. Le résumé et les en-têtes gardent leur hauteur lorsque le fichier ou le commit sélectionné change.

La sélection dans l’historique exprime immédiatement l’intention de l’utilisateur. Les détails, le fichier, son patch et ses couleurs affichés appartiennent à un même snapshot, remplacé quand la nouvelle préparation est complète. Les générations et annulations empêchent les réponses précédentes de remplacer ce snapshot. Aucun loader animé ne remplace le contenu pendant la lecture. Le loader d’ouverture d’un dépôt apparaît seulement après 500 ms et disparaît dès la fin ; une ouverture rapide affiche un fond sombre sans passer par l’accueil.

Par défaut, un clic explicite sur un fichier affiche `FileBrowser` au centre, avec les détails et la liste des fichiers à droite. `CodeView` partage le rendu du diff avec la vue compacte. L’entité `HistoryView` conserve ses pages, sa recherche et sa position pendant la consultation centrale ; elle est rendue à nouveau à la fermeture du fichier. Les deux vues utilisent le fond sombre du thème.

`syntax` analyse le texte en arrière-plan avec les grammaires Tree-sitter de GPUI Kit et un fallback lexical lorsque la grammaire ou sa requête est indisponible. Le langage est reconnu par l’extension ou le nom, notamment Cargo.lock, composer.lock, Makefile et .env. Les extraits Vue/Svelte/Astro utilisent leurs délimiteurs et le contexte du hunk pour amorcer les blocs script ou style ; un fragment ambigu ne permet pas de retrouver tout le contexte du fichier. Les versions anciennes et nouvelles de chaque hunk sont analysées séparément pour préserver les commentaires et chaînes multilignes sans mêler les suppressions aux ajouts. Un hunk isolé ne fournit pas le contexte syntaxique absent du patch. Les annotations « No newline at end of file » n’entrent pas dans le code reconstruit et s’affichent sans numéro de ligne.

La coloration est limitée à 2 000 lignes, 256 Kio de texte, 20 Kio par ligne et 20 000 tokens en sortie, avec un budget d’analyse de 500 ms. Les formats inconnus, fichiers binaires, limites dépassées et erreurs conservent le texte brut. Les tokens portent des catégories sémantiques ; `Palette` fournit leurs couleurs, donc changer de thème ne relance pas l’analyse. Un cache commun conserve huit analyses identifiées par le chemin et le fingerprint du contenu. `DiffCache` dans l’inspecteur conserve patches et tokens, avec un plafond de 256 fichiers, 8 Mio de texte cumulés et 200 000 tokens. Le fond avance séquentiellement avec une pause de 150 ms entre fichiers et s’arrête au plafond ; le fichier ouvert prend la priorité et peut évincer les anciennes entrées. Un changement de sélection ou de dépôt libère le cache de l’inspecteur et ignore les réponses tardives. Aucun cache de vue n’est conservé par onglet.

La sélection « Modifications non commitées » active la préparation progressive des fichiers indexés et non indexés. Leur clé associe la zone (`staged` ou `unstaged`) à la clé opaque du chemin Git ; ni le chemin affiché ni l’index de liste n’identifient ces patches. Le cache local est invalidé au début de chaque actualisation, puis reconstruit avec le nouveau statut, même si les chemins sont inchangés. Le dernier affichage cohérent est conservé pendant ces lectures. Le retour à un commit libère le cache local et arrête sa préparation ; une réponse de statut tardive ne la relance pas. La préparation des commits reste suspendue pendant la consultation des changements locaux. Un appel Git natif déjà lancé peut terminer après son annulation logique ; le cache conserve son emplacement de lecture de fond jusqu’au règlement effectif, pour éviter d’accumuler des lectures.

## Préférences d’interface

Le bouton « + » crée un onglet d’accueil avec les dépôts récents, filtrables par nom ou chemin. Ouvrir un dépôt réutilise cet onglet ; choisir un dépôt déjà ouvert active son onglet existant. Les onglets conservent seulement leur nom et leur chemin. Chaque activation recharge l’unique session et libère les données du dépôt précédent.

Les noms de références contenant `/` forment des dossiers imbriqués dans la sidebar. Les replis sont indépendants pour chaque catégorie de références et sont conservés pendant un rafraîchissement du même dépôt. Un filtre révèle temporairement les dossiers correspondants ; retirer le filtre restaure les replis précédents. Le choix d’une feuille conserve l’identité complète de sa référence Git.

Les cinq thèmes utilisent `theme::Palette`, y compris les couleurs du Canvas GPUI et des diffs. Classique, gris avec accents bleus, est le défaut ; il partage la palette syntaxique d’origine avec Mangrove, vert, et Macchiato, aux couleurs d’interface officielles Catppuccin. Ardoise, bleu ardoise orienté lecture, a un texte blanc cassé, des états à environ 7:1 sur les panneaux et sa propre palette syntaxique désaturée. Gitlab reprend les couleurs de la page GitLab observée dans Brave : fond presque noir, panneaux gris légèrement violets, liens bleu clair, couleurs de statuts et de diffs et coloration syntaxique. Les préférences sans thème reconnu chargent Classique. Trois rayons communs (`RADIUS_SM` 4 px, `RADIUS_MD` 6 px, `RADIUS_LG` 8 px) servent aux vues et aux contrôles GPUI Kit, quel que soit le thème. Le choix est chargé avant l’ouverture de la fenêtre. Un changement recolore le graphe sans rouvrir le dépôt.

Les types de changement partagent une même présentation : plus vert pour les ajouts, moins rouge pour les suppressions, crayon jaune pour les modifications et flèche bleue pour les renommages. Les statuts moins courants gardent un symbole distinct. Les listes de fichiers utilisent une ligne compacte avec le dossier atténué et le nom du fichier plus clair ; le chemin complet et le statut restent accessibles au survol. Les fonds de diff utilisent des couleurs dédiées par thème pour rendre les blocs ajoutés et supprimés plus visibles ; leurs gouttières de numéros sont un peu plus teintées, et les en-têtes de bloc sont teintés par l’accent du thème. Le code ordinaire et les numéros utilisent la couleur de lecture ; les catégories syntaxiques gardent les mêmes couleurs sur le contexte, les ajouts et les suppressions. `CodeView` gère la sélection et la copie du texte sans les gouttières.

La taille des textes est une préférence locale restaurée au démarrage. Les raccourcis Cmd/Ctrl avec `+` ou `=` augmentent la taille, avec `-` la réduisent et avec `0` rétablissent le défaut. Le diff possède une taille distincte, initialement à 11 px : les contrôles de `FileBrowser` l’ajustent sans changer le reste de l’interface. Cette préférence est partagée par les diffs de commits et de fichiers locaux, en vue centrale ou compacte, ainsi que le contenu et le blame. Les raccourcis globaux ajustent également le diff et le réinitialisent à 11 px avec `0`. L’accueil central conserve seulement le logo Mangrove, l’ouverture d’un dépôt et les accès récents.

`Preferences::pane_layout` calcule les largeurs effectives à partir des préférences des panneaux branches et détails. Le panneau des détails peut occuper tout l’espace restant après les branches et un historique d’au moins 340 px, sans plafond fixe ; réduire la fenêtre ne détruit pas la préférence pour une fenêtre plus grande. `Chrome` gère le déplacement des séparateurs, l’annulation par Escape, le clavier et la réinitialisation par double clic. `HistoryView` adapte ses colonnes et badges à la largeur mesurée de sa liste.

`SettingsView` occupe toute la fenêtre : le rendu du workspace est évité pendant son affichage, mais les entités conservent leur état. Retour ou Escape retrouve le workspace ; Cmd/Ctrl + K ferme les paramètres et la vue centrale pour focaliser la recherche lorsqu’un dépôt existe. À la réouverture, le brouillon de l’intervalle reprend la valeur persistée et les anciens messages de validation sont retirés.

## Profils et intégrations

`mangrove-remote` regroupe les profils et des adaptateurs HTTP en lecture seule, sans dépendance au moteur Git local. `IntegrationsView` lance les lectures sur l’exécuteur de fond GPUI. Les préférences, récents, comptes, favoris et choix SSH sont isolés par profil. Un changement de profil invalide les tickets de session, annule les lectures HTTP/SSH, libère les pages affichées et revient à un espace local vide. Les erreurs distantes ne bloquent pas la consultation locale.

Le sélecteur de dépôts conserve les résultats du compte courant et demande une page supplémentaire lorsque la fin du menu est visible. Un delegate spécifique garde les blocs de namespace déjà affichés ; les pages ajoutent des blocs à la fin pour conserver les positions de défilement et les indices utilisés par les confirmations différées du kit. Le menu et sa recherche restent ouverts. Une seule lecture est active, les IDs sont dédupliqués et l’accumulation est bornée à 20 000 dépôts / 8 Mio de textes et URLs. Une erreur arrête les lectures automatiques jusqu’à une reprise explicite ; un nouveau contexte remplace l’entité et invalide les callbacks précédents.

Les métadonnées sont enregistrées dans le répertoire de configuration Mangrove ; les tokens utilisent le coffre natif de l’OS, sans repli vers un fichier. Les objets renvoyés aux vues ne contiennent pas les secrets. Les requêtes HTTP de consultation exposent uniquement GET, avec TLS, absence de redirection, pagination restreinte au serveur et à la ressource demandée, délai et taille bornés. Voir [les intégrations](integrations.md) et [les adaptateurs par fournisseur](integrations-providers.md).

La connexion navigateur GitLab utilise un module OAuth séparé : PKCE S256, état aléatoire, callback temporaire limité à IPv4 loopback et scope `read_api`. Les seuls POST obtiennent ou renouvellent les tokens auprès de l’endpoint OAuth validé du serveur. Le bundle accès/refresh est une entrée du coffre ; les métadonnées contiennent seulement le type d’authentification et l’ID public de l’application. Les clients de lecture protègent les deux secrets dans leurs champs, URLs et curseurs. Une comparaison avant remplacement, coordonnée avec les autres opérations du coffre dans le processus, empêche un renouvellement de recréer un compte qui vient d’être déconnecté.

SSH consulte explicitement les branches et tags avec `git ls-remote`, en utilisant l’agent existant ou une clé déjà présente. Il ne récupère aucun objet et ne crée aucun cache Git. Il ignore les configurations Git et SSH susceptibles de lancer des commandes ; le serveur doit déjà être approuvé dans les fichiers `known_hosts`. Voir [le transport SSH](integrations-ssh.md).

La connexion navigateur GitHub utilise un module Device Flow séparé et le transport POST OAuth borné commun. Le navigateur reçoit uniquement la page de vérification validée ; le code court reste temporairement dans la vue et le device code secret reste dans le backend. L’attente en arrière-plan respecte les intervalles et l’annulation du contexte. Un paquet opaque distinct garde l’accès, la portée demandée et le renouvellement éventuel dans le coffre ; son identité lie profil, compte, serveur et Client ID. La rotation utilise la même coordination et la comparaison avant remplacement que GitLab. Le format des anciens comptes PAT et GitLab OAuth reste compatible.

L’auto-fetch historique reste une fonction distincte : il utilise Git et les credentials existants de la machine et écrit les objets et références distantes dans le dépôt local choisi. Les tokens et le choix SSH des intégrations ne lui sont pas transmis. Le clonage explicite est un service séparé de `mangrove-remote` : il réserve un nouveau dossier, lance Git en arrière-plan avec les credentials Git de la machine ou le choix SSH du profil, puis ouvre le résultat. Aucun token API n’est transmis à Git et aucun dossier existant n’est écrasé ou supprimé. Les paramètres ne contiennent plus la navigation des dépôts ; celle-ci est accessible depuis le nouvel onglet.

## Choix différés

Le remplacement de libgit2 par `gix` et une recherche de contenu historique ne sont pas engagés sans mesures sur des dépôts représentatifs. Le benchmark initial est une référence reproductible, pas une garantie de performances sur tous les monorepos.
