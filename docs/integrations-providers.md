# Intégrations distantes en lecture seule

Les adaptateurs de `mangrove-remote` lisent les dépôts accessibles au compte, les PR/MR ouvertes, leurs commentaires et les statuts CI du commit source. Toutes les requêtes de consultation REST passent par une interface **GET uniquement**. Les POST d’obtention et de renouvellement OAuth sont séparés. Aucun adaptateur ne modifie le dépôt Git local ou les ressources de la forge.

## Éditions et configuration

- **GitLab.com / GitLab Self-Managed / Dedicated** : URL du serveur HTTPS, par exemple `https://gitlab.com` ou `https://gitlab.example.com/gitlab`. Le client ajoute `/api/v4` et conserve le sous-chemin de déploiement. Les lectures sont les projets membres, les MR par projet, les discussions avec leurs notes et les pipelines filtrés par SHA. Sources : [projets](https://docs.gitlab.com/api/projects/), [MR](https://docs.gitlab.com/api/merge_requests/), [discussions](https://docs.gitlab.com/api/discussions/), [pipelines](https://docs.gitlab.com/api/pipelines/).
- **GitHub.com / GitHub Enterprise Server** : `https://github.com` utilise `https://api.github.com`; une URL Enterprise telle que `https://github.example.com` utilise `/api/v3`. Le client lit les dépôts du compte, les PR, les commentaires généraux **et** les commentaires de revue. Sources : [dépôts](https://docs.github.com/en/rest/repos/repos#list-repositories-for-the-authenticated-user), [PR](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests), [commentaires généraux](https://docs.github.com/en/rest/issues/comments#list-issue-comments), [revues](https://docs.github.com/en/rest/pulls/comments#list-review-comments-on-a-pull-request).
- **Bitbucket Cloud** : renseigner le workspace dans l'URL, par exemple `https://bitbucket.org/mon-workspace`. La forme `https://api.bitbucket.org/2.0/repositories/mon-workspace` est aussi acceptée. Le client utilise `api.bitbucket.org/2.0`, lit les dépôts de ce workspace accessibles au membre, les PR et tous les commentaires, y compris inline et réponses. La découverte globale des workspaces n'est pas implémentée; ajouter un compte par workspace. Sources : [dépôts du workspace](https://developer.atlassian.com/cloud/bitbucket/rest/api-group-repositories/), [PR et commentaires](https://developer.atlassian.com/cloud/bitbucket/rest/api-group-pullrequests/).
- **Bitbucket Server / Data Center** : URL HTTPS de l'installation, par exemple `https://bitbucket.example.com/bitbucket`. Le client ajoute `/rest/api/1.0`, lit `/repos`, les PR par projet/dépôt et les commentaires imbriqués des activités. Les formes de réponses implémentées correspondent aux références REST 8.x. Sources : [dépôts](https://developer.atlassian.com/server/bitbucket/rest/v809/api-group-repository/), [PR et activités](https://developer.atlassian.com/server/bitbucket/rest/v805/api-group-pull-requests/).

Renseigner la racine du serveur sans suffixe API pour GitLab, GitHub Enterprise et Bitbucket Server. Les ports HTTPS personnalisés sont acceptés pour les éditions auto-hébergées. Les identifiants dans l'URL, HTTP, fragments et paramètres de requête sont refusés.

## Jetons et droits minimaux

- **GitLab** : connexion navigateur OAuth PKCE avec une application publique et le scope `read_api`, transmise en Bearer ; un PAT avec `read_api` reste disponible en repli, transmis dans `PRIVATE-TOKEN`. Les accès restent limités par les droits du compte sur chaque projet. Le scope `api` accorde aussi des écritures et n'est pas nécessaire. Voir [la création de l’application Mangrove](integrations.md#connexion-gitlab-dans-le-navigateur). Sources : [OAuth PKCE](https://docs.gitlab.com/api/oauth2/), [scopes GitLab](https://docs.gitlab.com/security/tokens/access_token_scopes/).
- **GitHub** : PAT fine-grained limité aux dépôts nécessaires, avec `Metadata`, `Pull requests`, `Checks` et `Commit statuses` en lecture. `Contents` n'est pas exigé par ces endpoints. Le client utilise `Authorization: Bearer` et la version REST `2022-11-28`. Les politiques SSO et approbations d'organisation peuvent encore limiter l'accès. Sources : [permissions fine-grained](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens), [checks](https://docs.github.com/en/rest/checks/runs#list-check-runs-for-a-git-reference), [commit statuses](https://docs.github.com/en/rest/commits/statuses#list-commit-statuses-for-a-reference).
- **Bitbucket Cloud** : API token avec `read:repository:bitbucket` et `read:pullrequest:bitbucket`. Avec un e-mail Atlassian renseigné dans le compte, le client utilise Basic `email:token`; sans e-mail, il utilise Bearer. Bearer convient aux access tokens et, depuis le 18 août 2026, aux API tokens. Les access tokens doivent avoir les droits Repository Read et Pull requests Read correspondant à leur portée. Sources : [authentification et scopes](https://developer.atlassian.com/cloud/bitbucket/rest/), [support Bearer des API tokens](https://developer.atlassian.com/cloud/bitbucket/changelog/), [access tokens](https://support.atlassian.com/bitbucket-cloud/docs/using-access-tokens/).
- **Bitbucket Server / Data Center** : PAT/HTTP access token en Bearer, limité à la lecture des projets et dépôts concernés (`PROJECT_READ` / `REPO_READ`). Les droits effectifs du compte continuent de s'appliquer. Source : [HTTP access tokens](https://confluence.atlassian.com/bitbucketserver/personal-access-tokens-939515499.html).

Tester un compte charge la première page des dépôts. Cela ne certifie pas les droits sur chaque endpoint de commentaires ou CI; leur refus reste affiché lors de la lecture concernée. Un jeton expiré ou révoqué produit généralement HTTP 401; un refus de permission produit HTTP 403. Les réponses d'erreur de la forge ne sont pas exposées dans les diagnostics.

## CI et pagination

GitHub combine deux collections : check runs puis commit statuses historiques. GitLab présente les pipelines du SHA source. Bitbucket Cloud lit `/repositories/{workspace}/{repo}/commit/{sha}/statuses`; Bitbucket Server/Data Center lit `/projects/{project}/repos/{repo}/commits/{sha}/builds`, ce qui nécessite une version exposant cet endpoint. Le client ne lit pas les logs ou artefacts et ne relance pas de job. Sources : [statuts Cloud](https://developer.atlassian.com/cloud/bitbucket/rest/api-group-commit-statuses/), [builds Server/Data Center](https://developer.atlassian.com/server/bitbucket/rest/v810/api-group-builds-and-deployments/).

Une action charge une page. Les curseurs GitHub/GitLab utilisent `Link` (ou `X-Next-Page` pour GitLab), Cloud utilise `next` et Server/Data Center utilise `nextPageStart`. Un curseur est lié au compte et à la ressource; l'origine HTTPS, le chemin exact et les filtres sont vérifiés avant l'envoi du jeton. Les pages sont limitées à 50 éléments demandés, 200 éléments reçus et 200 commentaires cumulés par page, 100 pages par parcours et 4 Mio par réponse. Les curseurs ne sont pas sérialisés. Sources : [pagination GitLab](https://docs.gitlab.com/api/rest/), [pagination Cloud](https://developer.atlassian.com/cloud/bitbucket/rest/), [pagination Server](https://docs.atlassian.com/bitbucket-server/rest/7.20.0/bitbucket-build-rest.html).

GitLab complète ses liens avec les paramètres par défaut et les identifiants de route. Le client accepte uniquement les valeurs attendues pour chaque endpoint ; `id` et `noteable_id` doivent correspondre aux identifiants du chemin. Les filtres demandés, notamment `membership`, `state` et `sha`, restent obligatoires et inchangés, comme les paramètres ajoutés après la première page. Source : [génération des liens GitLab](https://gitlab.com/gitlab-org/gitlab/-/blob/master/lib/gitlab/pagination/offset_header_builder.rb#L54-61).

Les statuts CI sont normalisés en `success`, `failure`, `running`, `pending`, `cancelled`, `skipped`, `manual` ou `unknown`. Les fils GitLab et les réponses imbriquées Bitbucket Server sont conservés. Les commentaires GitHub et Bitbucket Cloud sont présentés individuellement, sans reconstruction de fils entre pages.

## Validation effectuée

`cargo test -p mangrove-remote --test providers` couvre les quatre adaptateurs avec réponses JSON réalistes et transport simulé : parcours dépôt → PR/MR → commentaires → CI, pagination, éditions auto-hébergées avec sous-chemin, séparation Basic/Bearer, révocation/expiration, limites d'API, annulation, réponses invalides et curseurs malveillants.

L’utilisateur a confirmé le fonctionnement de la connexion GitLab.com après correction de sa pagination. Les autres parcours et éditions restent à valider sur des comptes réels. Les adaptateurs suivent les documents primaires consultés le 1 octobre 2026 ; cela ne constitue pas une certification de chaque version serveur. Une recette sur une instance de chaque édition doit encore confirmer ses politiques de jetons, ses proxys, ses données et ses éventuelles extensions avant de revendiquer une compatibilité validée en production.
